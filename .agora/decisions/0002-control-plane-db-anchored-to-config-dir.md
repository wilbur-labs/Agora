# 0002. 控制平面库锚定 config.yaml 所在目录，全局一个库；歧义时拒绝启动而不是悄悄换库

- **Status**: accepted
- **Date**: 2026-09-04
- **Layer**: task:agora

## Context

W1-a 把项目搬进控制平面库之后，「哪个 SQLite 文件」这件事从「任务列表在哪」升级成了
「整个控制平面的身份在哪」。而它当前取决于**进程是从哪个目录启动的**。

`agora/config/settings.py::resolve_control_plane_db_path` 的四条优先级里，规则 2
（`memory.data_dir` + `agora.db`）和规则 4（`./data/agora.db`）都是相对**工作目录**解析的，
而随仓库发布的 `config.yaml` 正好命中规则 2：

```yaml
memory:
  data_dir: ./data
```

本机实测（2026-09-04）：

| 路径 | 大小 | 最后写入 |
|---|---|---|
| `D:\Projects\Agora\data\agora.db` | 1,343,488 B | 2026-08-29 18:34 |
| `D:\Projects\Agora\backend\data\agora.db` | 1,208,320 B | 2026-08-31 02:28 |

**这是两个内容不同的真实库，都不是空壳**，界面上没有任何东西说明当前用的是哪一个。
从仓库根 `make dev` 和从 `backend/` `make dev` 看到的是两套项目列表、两套任务列表。

这件事的记录史本身就是 [[adr/0015]] 的起源案例：`resolve_control_plane_db_path` 的 docstring 里
挂着一节标题为 *"Consequences this change deepened (accepted, not fixed here)"* 的散文，
把这个缺陷描述得**准确、诚实、详尽**——然后它在那里挂了三天，什么也没拦住。
2026-09-04 提交的 `3770783` 往 lifespan 里加了一行「启动时打印解析出的库路径」，
把它从**不可见**变成**可见**；可见之后缺陷照旧存在，这正是本 ADR 要收口的那一半。

CR-7 当时把这件事拆成两半：A（测试隔离）已做完提交，B（用哪个库取决于工作目录）推到 W2，
理由是 W2 就是 Environment 抽象，「项目在哪、跑在哪个环境」正是它要设计的。现在轮到 B。

## Decision

**其一，以 `config.yaml` 所在目录为根解析控制平面库的相对路径，整个控制平面仍然只有一个库。**
配置文件在哪，安装就在哪；启动目录不再参与决定身份。

**范围**（第五轮 P2-2 收窄一次，第六轮 P2-1 再收一次才准）。这份配置里的相对路径由**四条**
不同规则解析，取决于这条路径是**干什么用的**，而不是它写在文件哪一节：

| 规则 | 覆盖 |
|---|---|
| 锚定 `config.yaml` 所在目录 | `control_plane.db_path`、`memory.data_dir`（控制平面库**与** embeddings 库）、无数据根时放在 `registry_path` 旁边的那个库、`data/agora.db` 兜底 |
| 锚定 `ProjectRegistry.project_root`（默认 Agora 检出目录） | `registry_path` **所指的导入文件本身**、各项目的 `root`、`execution.allowed_workspace_roots`（**发布的 config.yaml 里没写这个键，但代码支持**，三个构造点各自锚定它） |
| 锚定**该项目自己解析出的 root** | 该项目的 `workspaces`。`importer._parse_project` 先解析 root、再拿 root 解析 workspaces，所以 `root: sub` + `codex: .agora/ws` 落在 `<registry root>/sub/.agora/ws` |
| **被覆盖，不是被解析** | `research.artifact_dir` / `research.workspaces`：只要配置里有 `projects` 键（随仓库发布的这份就有），`ResearchOrchestrator` 会用当前项目的值**整体覆写**这两项，文件里写什么都不生效。只有完全没有 `projects` 的配置才让它们相对进程 cwd |

**`registry_path` 同时出现在前两行，这不是笔误**：一个键两个消费者——本函数用它决定库放哪，
注册表用它打开那个文件本身。

**这段话改了五版才准**：第一版「本文件每条相对路径都锚定本文件目录」、第二版两条规则、
第三版三条、第四版四条、第五版补上 `allowed_workspace_roots`。每一版都对着代码的**一部分**
核过，然后**当成全部**说了出去。这不是笔误重复五次，是同一个动作缺了同一步：
**写全称句之前，先把被量化的集合完整列出来**。

第五版漏的那个尤其值得记：我确实做了穷举，但**是从 `config.yaml` 文件里穷举的**，
而 `allowed_workspace_roots` 只被代码支持、没写进发布的文件。
→ **判据加一条：要「配置支持的所有键」，权威来源是读它的代码，不是那份配置文件。**

原先 `config.yaml` 上写的是「本文件里每一条相对路径都锚定本文件所在目录」。那句话是假的，
却读起来像已经做到了——**同一个毛病，这次长在我自己用来标注边界的那句话里**，而且改了两轮
才真的准。

**其二，切换解析规则的同时必配启动检查，且这道检查覆盖歧义的两种形态，而不是一种。**

原先拍板的检查写法是：「锚定后的路径没有库、而旧的 cwd 相对路径有库时，拒绝启动并打印两个路径」。
**在本机它不会触发**——两个路径下都有库。那条检查只覆盖了歧义的一种形态，却被描述成
「这样就不会悄悄换库了」，即本项目反复出问题的那个形状：**声明的范围 > 检查的范围**。
所以实际采用的判据是：

> 旧的 cwd 相对解析与锚定后的解析**指向不同文件**，且**旧路径上确实存在一个库** →
> **拒绝启动，同时打印两个绝对路径**，不管锚定路径上有没有库。

四种情形：

| 锚定路径 | 旧 cwd 路径 | 处置 |
|---|---|---|
| 无库 | 有库 | **拒绝** —— 原方案唯一覆盖的一种 |
| 有库 | 有库（不同文件） | **拒绝** —— 本机的真实情形，原方案会静默通过 |
| 有库 | 无库 / 同一文件 | 正常启动，没有歧义 |
| 无库 | 无库 | 正常启动，全新安装 |

**其三，拒绝就是拒绝，不自动迁移、不自动挑一个。** 报错文本给出人可以执行的出路
（把库移到锚定路径，或在 `control_plane.db_path` 里写死绝对路径），由人来决定哪个库是真的。

## Consequences

- **本机这次改完，第一次启动一定会被拒绝。这是预期结果，不是 bug。** 两个库都在、内容不同，
  正是这道检查存在的理由；由用户决定保留哪一个。
- `resolve_control_plane_db_path` 的 docstring 里那节 "accepted, not fixed here" 随本次改动删除。
  它是 [[adr/0015]] 的起源案例，删掉它这件事本身就是那条 ADR 的验收。
- 检查是**一次性迁移期的护栏**，不是永久机制：等旧路径不再有库，它就再也不会触发。
  但不设过期时间——一个不触发的检查不花任何代价，而猜「什么时候可以拆」要花判断力。
- 相对路径的语义变了：写 `./data` 的用户从「跟着我 cd」变成「跟着 config.yaml」。
  这是**破坏性变更**，但破坏的是一个没人能依赖的行为（谁也没法依赖「从哪启动决定看到哪些项目」）。
- 仓库上挂着 #3/#4/#5 三个「clone 下来跑不起来」的 issue，都跟启动语义有关。锚定到 config.yaml
  目录**大概率改善**它们（不再要求从特定目录启动），但本 ADR 不声称修了它们——没验证过的改善不算数。
- `embeddings/store.py` 的 `vectors.db` 也读 `memory.data_dir`。**`VectorStore` 在 `agora/` 里没有
  任何生产调用点**（只有 `test_embeddings.py` 构造它，且那里的库要么显式传临时路径、要么
  经临时 `AGORA_CONFIG_PATH` 选出临时路径——总之从不落在真实安装上），所以它不是「第二个活着的
  库」——这条更正了 RESUME 里「vectors.db 是第二个库，一并处理」的说法（那是读了代码没读到调用点
  得出的，见 CR-13）。
  **但路径规则仍然一并改了**（评审第一轮 P1-6 指出的）：`config.yaml` 上写的是「本文件里每一条相对
  路径都锚定到本文件所在目录」，而 `vectors.db` 不锚定就让那句话变成假的——**又是「声明的范围 > 检查
  的范围」，只不过这次声明在注释里**。所以 `VectorStore` 同样锚定 `config_dir()`。
  **没有给它配歧义检查，也不需要**：没有生产调用点，就没有装在旧路径上的数据要被搬。磁盘上确认
  两处都没有 `vectors.db`。等它真被接回执行路径，就要补上同一道拒绝。

## Alternatives considered

- **每项目一个库（`<project>/.agora/agora.db`）** —— 否决。控制平面的行跨项目互相引用：
  任务引用项目、Run 引用任务、gate 引用 Run，队列 / attention / workflow 也跨项目。
  一项目一库会让这些引用无法在单个事务里写，等于推翻 W1-a 刚定下的「DB 是权威」。
  这是被否方案里唯一有真实吸引力的一个（它天然解决「项目搬家」），代价是重做一致性模型。
- **锚定 git 仓库根（`git rev-parse --show-toplevel`）** —— 否决。控制平面没有理由必须住在
  一个 git 仓库里；装出来的 Agora 就没有仓库。而且这会让「库在哪」依赖 git 是否可用，
  引入一个和数据无关的失败源。
- **保持 cwd 相对，只把它写清楚（文档 / docstring / 启动打印）** —— 否决，而且**这条已经试过了**。
  准确的散文在 docstring 里挂了三天，`3770783` 又加了启动打印；缺陷两次都活了下来。
  这正是 [[adr/0015]] 的判据：不会失败的东西保护不了任何东西。
- **自动迁移：把旧库复制/移动到锚定路径** —— 否决。前提是「旧库只有一个、且它是对的」，
  本机实测两个都在、内容不同。替用户挑一个，正是这次要防的那个「悄悄换库」，
  只不过换了个更自信的名字。
- **启动检查只覆盖「锚定处没有库、旧处有库」**（原拍板写法）—— 否决，理由见 Decision 其二。
  它在写下它的这台机器上就不会触发。**留在这里是因为它被否的方式最有教育意义**：
  一道窄于自己声明的检查比没有检查更坏，因为它读起来像证明。
