这一屏

  • 我定的右栏两态，不是固定内容。Run 跑着 → 整块换成实时终端（live-terminal 提案的 P1/P2）；Run 结束 → 改动 + 提交门禁。这两组信息天然互斥地被需要，所以不用在「挤」和「砍」之间选。CR / ADR 移回左栏——它们是项目级信息，不该常驻在任务级的右栏，而且左栏本来就有入口，是重复。
  • 我定的Run 之间不画连线，用嵌套。连线会很快变成面条图（一个 worker 可能被复核、失败重试、再复核）。而关系数据本来就有：reviews_run_id 明确指向被复核的 Run。所以复核和重试缩进挂在它们所属的 worker Run 下面，顶层时间线只排 worker。这样读起来是「今天做了 2 件事」，不是「发生了 5 个事件」——跟「原语是 Run 不是聊天」同一个道理：按工作单元排，不按进程启动次数排。
  • 我定的执行者和环境在派活那一刻选（底部消息框旁的两个下拉），不在导航里，也不在 Today 里。
  • 留意左栏多了一项「已知缺陷 5」。D-1~D-5 不该只活在 RESUME 的文字里——它们是这个项目的真实负债，值得在界面上一直可见。

这一屏

  • 我的建议脱敏这件事，先分类，别指望脱敏。机械扫描只能抓「长得像敏感信息」的东西——IP、主机名、邮箱、公司名。它抓不到真正危险的那类：业务流程本身。「回付文書選択 → 履歴ページに追記 → チケットに書き戻す」这段里一个 IP 都没有，泄露的却是内部流程。
    更关键：一条需要脱敏才能公开的技能，脱敏之后往往也没剩下什么价值。你现在 18 条本来就天然分成两堆（上表已分组）——干净的 10 条直接可上，带内网信息的 3 条本来就该留本地。所以机制是：默认不上传 → 写的时候就分层 → 机械闸当最后一道 → 上传前必看 diff 预览。
  • 我的建议「被用 N 个项目」不做，换成「安装在 N 个」+「最后更新」。两个理由：① 拿不到真信号——Claude 的 skill 由模型自主决定是否加载（渐进披露），Agora 在进程外观测不到；你能记的只有「我装了哪些」，那是「可用」不是「被用」。② 假精度比没有更糟——一个「被 5 个项目使用」的数字会让你以为它重要，而它可能一次都没真正加载过。
    替代信号是 Agora 自己就有的事实、不会撒谎：「安装在 3 个项目」反映你的判断，「最后更新 08-27」反映它还活不活着。真需要使用率那天，可以从 Claude Code 的 session.jsonl 里挖——那是后话。
  • 已定Claude skill 格式是唯一真源，Codex / Kiro 是单向编译产物。三家加载语义根本不同，最小公约数格式三边都不好用。改一次，重新编译两份。
  • 砍掉不做「检测到重复解法 → 自动生成 skill」。v0.1-0.4 的 skills/extractor.py 就是这个，已随议会一起删除。这是实证，不是猜测。
